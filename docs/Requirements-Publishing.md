# ТЗ: Публикация PlantUML Studio и реализация автоматических обновлений

**Репозиторий:** https://github.com/Kickchat/plantuml-studio

**Целевая платформа:** macOS

**Цель:** организовать полноценный процесс публикации, сборки, версионирования и автоматического обновления PlantUML Studio через GitHub.

## Этап 1. Публикация проекта в GitHub

**Это обязательный первый этап. К настройке автообновлений переходить только после успешной публикации проекта.**

### 1.1. Подготовка репозитория

1. Проверить текущее состояние локального проекта.
2. Проверить подключение к удалённому репозиторию `Kickchat/plantuml-studio`.
3. Если Git не инициализирован, выполнить инициализацию.
4. Если удалённый репозиторий недоступен, проверить права доступа и авторизацию. Не создавать другой репозиторий без согласования.
5. Настроить `.gitignore` для macOS, Xcode и используемого технологического стека.
6. Исключить из публикации:
   - Локальные настройки IDE.
   - Временные файлы и кэш.
   - Секреты, токены и пароли.
   - Сертификаты и приватные ключи.
   - Локальные артефакты сборки.
   - Пользовательские данные.

### 1.2. Первичная публикация

- Проверить историю Git и отсутствие секретов в публикуемых коммитах.
- Сохранить актуальную версию исходного кода.
- Проверить наличие `README.md` с описанием проекта и инструкцией по сборке.
- Проверить наличие подходящей лицензии. Не выбирать и не менять лицензию без согласования.
- Создать коммит с текущим состоянием проекта.
- Отправить проект в `https://github.com/Kickchat/plantuml-studio`.
- Если удалённый репозиторий уже содержит историю, сначала согласовать её с локальной. Не использовать принудительную перезапись.
- Убедиться, что проект успешно опубликован и может быть клонирован и собран из чистого окружения.

**Критерий готовности:** актуальный исходный код находится в указанном GitHub-репозитории, история сохранена, проект успешно собирается после клонирования.

## Этап 2. Версионирование приложения

Внедрить единый механизм версионирования.

Использовать Semantic Versioning:

- `0.1.0` - первая тестовая версия.
- `0.2.0` - новая функциональность.
- `0.2.1` - исправление ошибок.
- `1.0.0` - первый стабильный релиз.

### Требования

1. Версия приложения должна соответствовать опубликованному релизу.
2. Настроить `CFBundleShortVersionString` и `CFBundleVersion` для нативного macOS-приложения.
3. Обеспечить автоматическую синхронизацию версий при релизной сборке.
4. Добавить отображение версии в меню «О PlantUML Studio».
5. Добавить `CHANGELOG.md`.
6. Использовать Git-теги вида `v0.2.0`.
7. Исключить возможность повторной публикации релиза с уже существующей версией.

## Этап 3. Автоматическая сборка через GitHub Actions

Настроить CI/CD для macOS.

### 3.1. Проверка изменений

При создании Pull Request:

- Проверять корректность проекта.
- Запускать доступные автоматические тесты.
- Проверять успешность сборки.
- Не публиковать релизные артефакты.

### 3.2. Релизная сборка

При публикации нового Git-тега формата `v*`:

1. Запускать GitHub Actions.
2. Получать исходный код соответствующего коммита.
3. Подготавливать окружение сборки.
4. Собирать PlantUML Studio в Release-конфигурации.
5. Проверять корректность версии.
6. Подписывать приложение сертификатом Developer ID.
7. Выполнять Apple notarization.
8. Формировать дистрибутив `.dmg` или `.zip`.
9. Создавать GitHub Release.
10. Прикреплять готовую сборку к релизу.
11. Формировать описание изменений на основе Git-истории.

Секреты Apple Developer хранить исключительно в GitHub Actions Secrets.

**Важно:** при отсутствии сертификатов или необходимых доступов не обходить проверки безопасности. Подготовить инфраструктуру и предоставить инструкцию по завершению настройки.

## Этап 4. Автоматическое обновление PlantUML Studio

Реализовать механизм обновления установленного приложения.

Для нативного macOS-приложения использовать **Sparkle 2**, если текущая архитектура позволяет его интегрировать. Для другого технологического стека выбрать совместимый механизм с аналогичными возможностями.

### 4.1. Проверка обновлений

Приложение должно:

1. Проверять наличие новой версии при запуске.
2. Выполнять периодическую проверку в фоновом режиме.
3. Сравнивать установленную версию с опубликованной.
4. Не предлагать уже установленную или более старую версию.
5. Не блокировать запуск при недоступности GitHub или сервера обновлений.

### 4.2. Уведомление пользователя

При обнаружении новой версии показывать стандартное окно обновления с информацией:

- Текущая версия.
- Доступная версия.
- Список изменений.
- Возможность установить обновление.
- Возможность отложить установку.

Предусмотреть пункт меню:

**PlantUML Studio → Проверить обновления**

### 4.3. Загрузка и установка

После подтверждения пользователя:

1. Скачать новую сборку.
2. Проверить цифровую подпись обновления.
3. Проверить целостность пакета.
4. Подготовить установку.
5. Проверить наличие несохранённых изменений в редакторе.
6. При необходимости предложить сохранить изменения.
7. Установить новую версию штатным механизмом обновления.
8. Перезапустить приложение после успешной установки.

**Ключевое требование:** пользователю не нужно вручную скачивать `.dmg`, удалять старую версию или переносить новую в Applications.

Обновление должно происходить непосредственно из установленного приложения.

### 4.4. Сохранность данных

При обновлении должны сохраняться:

- Пользовательские настройки.
- Выбранная тема оформления.
- Локальные проекты и диаграммы.
- Настройки редактора.
- История недавно открытых файлов.

Обновление не должно приводить к потере пользовательских данных.

## Этап 5. Интеграция Sparkle с GitHub Releases

Реализовать инфраструктуру доставки обновлений.

### Требования

1. Использовать GitHub Releases как источник релизных сборок.
2. Настроить генерацию Sparkle appcast.
3. Обеспечить публикацию и обновление appcast при выпуске нового релиза.
4. Настроить подпись обновлений ключом Sparkle.
5. Хранить приватный ключ в защищённом хранилище секретов.
6. Проверять соответствие версии, подписи и URL скачивания.
7. Исключить установку неподписанных или подменённых пакетов.
8. Не включать отладочные сборки в стабильный канал обновлений.

Проверить доступность канала обновлений для пользователей. Если GitHub Releases недоступен из пользовательской сети, предусмотреть возможность переноса дистрибутивов и appcast на другой HTTPS-хостинг без изменения архитектуры приложения.

---

## Этап 6. Каналы обновлений

Предусмотреть архитектурную поддержку двух каналов.

**Stable**
- Проверенные релизы.
- Рекомендуемый канал по умолчанию.

**Beta**
- Предварительные сборки.
- Тестирование новых возможностей.
- Возможность включения через настройки приложения в будущем.

На первом этапе достаточно полностью реализовать Stable. Beta не должна усложнять выпуск первой рабочей версии.

---

## Этап 7. Тестирование

Обязательно проверить следующие сценарии:

| Сценарий | Ожидаемый результат |
|---|---|
| Новая версия отсутствует | Приложение работает без уведомлений |
| Доступна новая версия | Пользователь получает предложение обновиться |
| Пользователь отклонил обновление | Приложение продолжает работать |
| Интернет недоступен | Ошибка не блокирует приложение |
| Загрузка прервана | Приложение остаётся работоспособным |
| Пакет повреждён | Установка отклоняется |
| Подпись недействительна | Установка отклоняется |
| Есть несохранённая диаграмма | Данные не теряются |
| Обновление установлено | Запускается новая версия |
| Повторная проверка | Установленная версия не предлагается повторно |

Дополнительно протестировать полный сценарий обновления с одной подписанной релизной версии на следующую.

## Этап 9. Итоговый результат

После реализации должен работать следующий процесс:

1. Разработчик завершает работу над новой функциональностью.
2. Изменения проходят проверку и попадают в `main`.
3. Создаётся новый Git-тег.
4. GitHub Actions автоматически собирает приложение.
5. Выполняется подпись и notarization.
6. Готовая сборка публикуется в GitHub Releases.
7. Обновляется источник информации о новых версиях.
8. Установленная PlantUML Studio обнаруживает обновление.
9. Пользователь подтверждает установку.
10. Приложение обновляется без ручной переустановки.

## Ограничения для агента

- Сначала изучить реальный стек и архитектуру проекта.
- Не переписывать существующие компоненты без необходимости.
- Сохранить текущую функциональность редактора PlantUML.
- Не удалять пользовательские данные.
- Не использовать небезопасные механизмы обновления.
- Не хранить приватные ключи и сертификаты в репозитории.
- Не выполнять force push.
- Не публиковать стабильный релиз без успешного тестирования.
- При отсутствии необходимых сертификатов или доступов остановиться на соответствующем шаге и запросить их настройку.
- После публикации исходного кода дальнейшую разработку вести в отдельной ветке.
- Не выполнять merge в `main` без подтверждения.
