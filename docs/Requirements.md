# Техническое задание: PlantUML Studio
## Разработка MVP приложения для macOS

### 1. Цель проекта

Разработать нативное приложение для macOS, объединяющее текстовый редактор PlantUML и структурный визуальный конструктор диаграмм.

Приложение должно позволять пользователю создавать и редактировать диаграммы двумя способами:

1. Написанием и редактированием исходного PlantUML-кода.
2. Использованием визуального конструктора без необходимости вручную писать код.

**Ключевая особенность: полноценная двусторонняя синхронизация.**

- Изменение PlantUML-кода обновляет визуальный конструктор.
- Изменение элементов через конструктор обновляет исходный PlantUML-код.
- Изменения не должны уничтожать комментарии, форматирование и другие конструкции, не затронутые редактированием.
- Результат должен соответствовать официальному синтаксису PlantUML.

Приложение должно работать локально, без обязательного подключения к интернету, регистрации и облачных сервисов.

### 2. Источник требований по PlantUML

К задаче будет приложен полный гайд по PlantUML.

**Перед началом реализации агент обязан:**

1. Изучить предоставленный гайд.
2. Выделить официально поддерживаемые конструкции Sequence Diagram и ER Diagram.
3. Определить синтаксис создания, редактирования и удаления элементов.
4. Составить матрицу поддерживаемых возможностей.
5. Проверить синтаксические особенности, ограничения и допустимые комбинации конструкций.
6. Использовать гайд как основной источник при проектировании парсера и конструктора.

Необходимо учитывать, что документация может описывать несколько способов записи одной конструкции.

Агент должен выбирать корректный вариант и обеспечивать чтение альтернативных форм там, где это реализовано.

Запрещено самостоятельно придумывать синтаксис PlantUML или генерировать неподдерживаемые конструкции.

Если функция не предусмотрена PlantUML, её нельзя представлять как официально поддерживаемую.

Если функция предусмотрена PlantUML, но не реализована в конструкторе MVP, соответствующий код должен сохраняться без изменений.

### 3. Поддерживаемые типы диаграмм

MVP должен поддерживать два типа:

- Sequence Diagram
- Entity Relationship Diagram (ERD), реализуемую средствами PlantUML Information Engineering

Каждый тип должен иметь собственный набор визуальных инструментов и свойств.

Архитектура должна предусматривать возможность добавления других типов диаграмм в будущем без переработки общих компонентов.

# 4. Интерфейс приложения

## 4.1. Общая концепция

Нативное приложение macOS с минималистичным интерфейсом.

Рекомендуемый технологический стек:

- Swift
- SwiftUI
- AppKit при необходимости
- WKWebView с CodeMirror 6 для редактирования кода
- Официальный движок PlantUML для рендеринга

Допускается изменение конкретных технологий при наличии технического обоснования.

Интерфейс должен соответствовать актуальным принципам macOS Human Interface Guidelines.

## 4.2. Основные области интерфейса

**Левая область: PlantUML Code Editor**

Функциональность:

- Редактирование PlantUML-кода.
- Подсветка синтаксиса.
- Нумерация строк.
- Автоматические отступы.
- Подсветка парных конструкций.
- Поиск и замена.
- Отображение синтаксических ошибок.
- Undo/Redo.
- Поддержка стандартных сочетаний клавиш macOS.

**Центральная область: Diagram Preview**

Функциональность:

- Отображение диаграммы, сформированной официальным движком PlantUML.
- Масштабирование.
- Перемещение области просмотра.
- Автоматическое вписывание диаграммы в окно.
- Выбор поддерживаемых элементов для редактирования.
- Контекстные действия для элементов.
- Обновление после изменения исходного кода.

**Правая область: Properties / Constructor**

Контекстная панель визуального редактирования.

Содержимое зависит от выбранного типа диаграммы и элемента.

Например, при выборе сообщения Sequence Diagram:

- Отправитель.
- Получатель.
- Тип стрелки.
- Текст сообщения.
- Доступные параметры сообщения.
- Удаление.
- Изменение порядка.

При выборе сущности ER Diagram:

- Название сущности.
- Алиас.
- Атрибуты.
- Ключевые поля.
- Связи.
- Доступные параметры оформления.

Панели должны поддерживать изменение размеров и скрытие.

## 4.3. Режимы отображения

Предусмотреть:

- Code + Diagram + Properties.
- Code + Diagram.
- Только код.
- Только диаграмма с доступом к конструктору.

Необходимо поддержать горизонтальное и вертикальное разделение кода и диаграммы.

## 4.4. Вкладки

Реализовать:

- Открытие нескольких `.puml` файлов.
- Переключение между вкладками.
- Индикатор несохранённых изменений.
- Подтверждение при закрытии несохранённого документа.
- Сохранение состояния открытых документов в рамках возможностей macOS.

# 5. Sequence Diagram

Реализовать структурный визуальный конструктор Sequence Diagram.

## 5.1. Участники

Поддержать предусмотренные официальным PlantUML типы участников, включая:

- actor
- participant
- boundary
- control
- entity
- database
- collections
- queue

Действия:

- Создать участника.
- Изменить название.
- Изменить алиас.
- Изменить поддерживаемый тип.
- Удалить участника.
- Изменить порядок объявления участников.
- Настроить поддерживаемые свойства.

Переименование алиаса должно корректно обновлять ссылки на участника.

## 5.2. Сообщения

Поддержать документированные типы сообщений и стрелок, включая:

- Обычные вызовы.
- Ответы.
- Асинхронные сообщения.
- Сообщения самому себе.
- Другие официально поддерживаемые варианты стрелок, включённые в матрицу MVP.

Действия:

- Добавить сообщение.
- Изменить отправителя.
- Изменить получателя.
- Изменить текст.
- Изменить тип стрелки.
- Удалить сообщение.
- Изменить порядок сообщений.

При изменении порядка необходимо сохранять корректность вложенных блоков.

## 5.3. Управляющие блоки

Поддержать:

- alt
- else
- opt
- loop
- par
- break
- critical
- group

Возможности:

- Создание блока.
- Изменение условий и подписей.
- Добавление ветвей там, где это допускается синтаксисом.
- Добавление сообщений внутрь блока.
- Удаление блока.
- Перемещение блока.
- Изменение порядка элементов внутри блока.
- Поддержка вложенных блоков.

Визуальный конструктор должен отображать иерархию блоков.

Недопустимо создание некорректной вложенности.

## 5.4. Активации

Поддержать официальные конструкции:

- activate
- deactivate
- destroy

А также другие формы управления активацией, если они включены в матрицу MVP.

Конструктор должен позволять редактировать активации без нарушения корректности исходной диаграммы.

## 5.5. Дополнительные элементы

Реализовать основные документированные возможности:

- Notes.
- Разделители.
- Задержки.
- Заголовки.
- Автонумерацию сообщений.

Поддерживаемые свойства и варианты синтаксиса определять по приложенному гайду.

# 6. ER Diagram

Реализовать конструктор ER Diagram на основе официальных возможностей PlantUML.

## 6.1. Сущности

Действия:

- Создать сущность.
- Изменить название.
- Изменить алиас.
- Удалить сущность.
- Изменить порядок объявления.
- Редактировать поддерживаемые свойства оформления.

Использовать официальный синтаксис `entity`.

## 6.2. Атрибуты

Поддержать:

- Добавление атрибутов.
- Переименование.
- Изменение типа данных, указанного пользователем.
- Удаление.
- Изменение порядка.
- Обозначение ключевых атрибутов.
- Разделители атрибутов.

Конструктор должен сохранять допустимое представление атрибутов PlantUML.

Необходимо различать визуальное обозначение поля и фактические ограничения базы данных.

PlantUML не должен рассматриваться как полноценный SQL DDL.

## 6.3. Связи

Реализовать создание и редактирование связей между сущностями.

Поддержать документированные обозначения кардинальности, включая:

- Один к одному.
- Один ко многим.
- Ноль или один.
- Ноль или много.
- Один или много.

Действия:

- Создать связь.
- Выбрать исходную сущность.
- Выбрать целевую сущность.
- Изменить кардинальность с каждой стороны.
- Изменить подпись.
- Изменить поддерживаемый тип линии.
- Удалить связь.

Все комбинации должны проверяться на соответствие официальному синтаксису.

## 6.4. Ограничения

Не реализовывать в MVP:

- Генерацию SQL-схем.
- Подключение к реальной БД.
- Автоматическую миграцию БД.
- Автоматическое создание физических внешних ключей.
- Произвольное позиционирование сущностей.

Возможность расширения должна сохраняться архитектурно.

# 7. Двусторонняя синхронизация

Это наиболее важная техническая часть проекта.

## 7.1. Общая модель

Рекомендуемая архитектура:

PlantUML Source ↔ Parser / Document Model ↔ Visual Constructor

Отдельно:

PlantUML Source → Official PlantUML Renderer → Diagram Preview

Исходный текст является основным документом.

Промежуточная модель используется для анализа структуры и применения визуальных операций.

## 7.2. Изменение кода

При изменении исходного кода:

1. Выполняется разбор поддерживаемых конструкций.
2. Обновляется внутренняя модель.
3. Обновляется структурный конструктор.
4. Запускается обновление диаграммы.
5. При ошибке отображается диагностика.

Необходимо предусмотреть debounce, чтобы не выполнять тяжёлый рендеринг после каждого нажатия клавиши.

## 7.3. Изменение конструктора

При изменении элемента через конструктор:

1. Определяется соответствующий элемент исходного кода.
2. Проверяется допустимость операции.
3. Формируется минимальное текстовое изменение.
4. Изменение применяется к исходному документу.
5. Обновляется редактор кода.
6. Обновляется визуальная диаграмма.

**Запрещено полностью перегенерировать исходный файл при каждом визуальном изменении.**

## 7.4. Сохранение исходного кода

Обязательно сохранять:

- Комментарии.
- Отступы.
- Пустые строки.
- Алиасы.
- Пользовательское форматирование.
- Неизменённые конструкции.
- Неизвестные или неподдерживаемые визуальным конструктором элементы.

Для этого использовать source ranges, стабильную идентификацию элементов в рамках документа и точечные текстовые изменения.

## 7.5. Неподдерживаемый синтаксис

Если документ содержит корректную PlantUML-конструкцию, которую конструктор не умеет редактировать:

- Сохранять её исходный текст.
- По возможности отображать результат через официальный рендерер.
- Не разрешать небезопасные визуальные операции над этой конструкцией.
- Показывать понятное уведомление об ограничении.

Нельзя удалять или переписывать неизвестный синтаксис.

## 7.6. Ошибки

При синтаксической ошибке:

- Не уничтожать исходный текст.
- Показывать сообщение об ошибке.
- Подсвечивать соответствующий участок, если его можно определить.
- Сохранять последнее корректное состояние структурного конструктора, явно обозначив его неактуальность.
- Блокировать визуальные операции, если невозможно гарантировать корректное применение изменений.

# 12. Тестирование

## 12.1. Unit Tests

Проверить:

- Разбор участников Sequence.
- Разбор сообщений.
- Разбор вложенных управляющих блоков.
- Разбор сущностей ER.
- Разбор атрибутов.
- Разбор кардинальностей.
- Переименование элементов.
- Добавление и удаление элементов.
- Применение точечных изменений.
- Сохранение комментариев и форматирования.

## 12.2. Integration Tests

Проверить:

- Code → Constructor.
- Constructor → Code.
- Code → Renderer.
- Constructor → Code → Renderer.
- Сохранение и повторное открытие файлов.
- Обработку неподдерживаемых конструкций.
- Обработку синтаксических ошибок.

## 12.3. Round-trip Tests

Обязательные проверки:

1. Открыть существующий `.puml`.
2. Разобрать документ.
3. Не выполняя изменений, сохранить документ.
4. Убедиться, что содержимое осталось идентичным.

Для визуального редактирования:

1. Открыть документ.
2. Изменить один элемент через конструктор.
3. Убедиться, что изменился только необходимый участок исходного текста.
4. Проверить корректность итогового PlantUML.
5. Сохранить и повторно открыть файл.

## 12.4. Регрессионные тесты

Создать набор тестовых `.puml` файлов:

- Простая Sequence.
- Сложная Sequence с вложенными блоками.
- Sequence с комментариями и алиасами.
- Простая ER.
- ER с несколькими связями.
- ER с различными кардинальностями.
- Документы с неподдерживаемыми конструктором конструкциями.
- Документы с ошибками синтаксиса.

По возможности использовать примеры из приложенного гайда.

# 13. UX-требования

Приложение должно быть ориентировано на повседневную работу с диаграммами.

Приоритеты:

1. Минимальное количество действий для добавления элемента.
2. Быстрое переключение между кодом и конструктором.
3. Понятное редактирование свойств.
4. Стабильная синхронизация.
5. Удобная навигация по большим диаграммам.
6. Отсутствие визуальной перегруженности.

Для Sequence предусмотреть структурное дерево сообщений и блоков.

Для ER предусмотреть список сущностей, атрибутов и связей.

Добавление элементов должно выполняться через контекстные действия и соответствующие кнопки конструктора.

Не реализовывать произвольное рисование элементов мышью, свободное размещение объектов и координатный редактор.

# 17. Критерии приёмки

MVP считается готовым, если:

- Приложение запускается на целевой версии macOS.
- Sequence Diagram открываются и отображаются.
- ER Diagram открываются и отображаются.
- Поддерживаемые элементы можно создавать через конструктор.
- Поддерживаемые элементы можно редактировать через конструктор.
- Изменения конструктора отражаются в PlantUML-коде.
- Изменения кода отражаются в конструкторе.
- Диаграммы рендерятся официальным движком.
- Исходные комментарии и форматирование сохраняются при незатрагивающих их операциях.
- Неизвестные конструкции не удаляются автоматически.
- Ошибки не приводят к потере исходного документа.
- Работают Undo/Redo.
- Работают открытие и сохранение файлов.
- Работает экспорт SVG и PNG.
- Пройдены автоматические тесты.
- Приложение функционирует без обязательного интернета.

Все заявленные функции должны быть реализованы, а не представлены демонстрационными заглушками.

## Основной принцип

**PlantUML Studio должен быть прежде всего надёжным редактором PlantUML, а не графическим приложением, которое лишь имитирует работу с PlantUML.**

Исходный код остаётся основным документом. Конструктор является удобным интерфейсом для выполнения допустимых операций над этим документом.

Корректность синтаксиса, сохранность пользовательского кода и двусторонняя синхронизация имеют более высокий приоритет, чем визуальные эффекты и дополнительные функции.

При возникновении архитектурных сложностей агент должен выбирать решение, которое обеспечивает сохранность исходного документа и возможность последующего расширения приложения.
