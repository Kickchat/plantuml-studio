# ТЗ: Переработка конструктора PlantUML Studio
## Semantic Constructor & Diagram Navigation

### 1. Цель задачи

Переработать существующую правую панель «Конструктор» в PlantUML Studio.

Сейчас конструктор фактически дублирует исходный PlantUML-код, отображая отдельные строки документа, включая `skinparam`, `autonumber`, объявления участников и другие технические конструкции.

Необходимо превратить его в **полноценный структурный редактор объектов диаграммы**, позволяющий просматривать, создавать, изменять и удалять элементы без необходимости вручную редактировать PlantUML-код.

**Основной принцип: пользователь должен понимать структуру диаграммы и управлять её элементами, не читая исходный код.**

При этом необходимо сохранить двустороннюю синхронизацию между конструктором и редактором PlantUML.

---

### 2. Общие требования

1. Использовать существующую архитектуру приложения.
2. Не создавать второй независимый парсер PlantUML.
3. Использовать существующую модель документа и механизм синхронизации.
4. Не изменять официальную семантику PlantUML.
5. Не перегенерировать весь исходный документ при редактировании одного элемента.
6. Сохранять комментарии, форматирование и неподдерживаемые конструкции.
7. Не изменять существующую логику рендеринга диаграмм без необходимости.
8. Поддерживать светлую и тёмную темы приложения.
9. Использовать нативные элементы SwiftUI/AppKit.

Перед реализацией изучить существующий код конструктора, парсера, моделей и редактора.

---

# 3. Новая структура конструктора

Правая панель должна состоять из трёх логических областей:

1. **Панель управления:** поиск, добавление объектов.
2. **Структура диаграммы:** иерархическое дерево объектов.
3. **Свойства выбранного элемента:** контекстный редактор параметров.

Все области должны работать с семантическими объектами, а не с отдельными строками исходного кода.

## 3.1. Панель управления

В верхней части разместить:

- Поле поиска по объектам диаграммы.
- Кнопку `+` для добавления элементов.
- Контекстное меню доступных типов элементов.

Список доступных элементов зависит от типа диаграммы.

Для Sequence:

- Участник.
- Сообщение.
- Условный блок.
- Цикл.
- Заметка.
- Разделитель.
- Другие поддерживаемые конструкции.

Для ER:

- Сущность.
- Атрибут.
- Связь.

Действия, недопустимые в текущем контексте, должны быть недоступны.

# 4. Sequence Diagram

## 4.1. Раздел «Участники»

Отображать список всех участников диаграммы.

Каждый элемент должен содержать:

- Название участника.
- Тип участника.
- Цветовой индикатор, если цвет явно задан.
- Иконку соответствующего типа.

Пример:

**Участники (3)**

- Client · Boundary
- Service · Participant
- Worker · Participant

Не показывать пользователю исходные объявления вида:

`boundary Client as client #DDDDFF`

Вместо этого отображать читаемое название и свойства.

При выборе участника открывать редактор:

- Название.
- Алиас.
- Тип.
- Цвет, если поддерживается.
- Другие допустимые параметры.

Предусмотреть переименование, удаление и изменение порядка участников.

Переименование алиаса должно обновлять все связанные ссылки.

## 4.2. Раздел «Сценарий»

Отображать последовательность взаимодействий в виде иерархического дерева.

Каждое сообщение должно содержать:

- Название сообщения.
- Отправителя.
- Получателя.
- Иконку направления взаимодействия.

Пример:

**Проверка входных данных**

- Отправить запрос
  - Client → Service
- Переход в validation_state
  - Service → Worker
- ALT: Проверка запроса
  - Ветка: request_valid = true
  - Ветка: request_valid = false
    - Проверка данных
    - Результат обработки
- OPT: Обработка результата
  - Отправка сообщения
  - Результат обработки

Дерево должно отражать реальную вложенность PlantUML.

### 4.2.1. Управляющие блоки

Отображать `alt`, `opt`, `loop`, `par`, `break`, `critical` и `group` как отдельные структурные элементы.

Требования:

- Возможность сворачивать и разворачивать блоки.
- Отображение названия или условия.
- Отображение вложенных сообщений.
- Отображение ветвей `else`.
- Возможность выбора блока целиком.
- Возможность выбора отдельной ветви.
- Контекстное меню допустимых операций.

Вложенность должна соответствовать исходному документу.

### 4.2.2. Сообщения

Сообщение должно отображаться как самостоятельный объект.

Основной текст: название сообщения.

Дополнительный текст: отправитель → получатель.

Например:

**Проверка данных**

`Worker → Worker`

При выборе сообщения отображать свойства:

- Отправитель.
- Получатель.
- Текст сообщения.
- Тип стрелки.
- Допустимые дополнительные параметры.

### 4.2.3. Заметки

Заметки должны отображаться отдельными объектами.

Показывать краткий текст заметки и связанный элемент, если связь определена.

При выборе открывать редактор содержимого и поддерживаемых параметров.

# 5. ER Diagram

Для ER реализовать аналогичный структурный конструктор.

## 5.1. Раздел «Сущности»

Отображать сущности по названиям.

Пример:

**Сущности (3)**

- Customer
  - id · UUID · PK
  - name · VARCHAR
  - email · VARCHAR
- Order
  - id · UUID · PK
  - customer_id · UUID
- Payment
  - id · UUID · PK

Требования:

- Сворачивание сущностей.
- Отображение вложенных атрибутов.
- Создание и удаление сущностей.
- Добавление и изменение атрибутов.
- Изменение порядка атрибутов.
- Редактирование названия и алиаса.

Обозначения PK и другие свойства должны соответствовать реально поддерживаемому синтаксису PlantUML.

Не выводить семантику ограничений БД из одного лишь названия атрибута.

## 5.2. Раздел «Связи»

Отображать связи отдельно от сущностей.

Пример:

**Связи (2)**

- Customer → Order · 1:N
- Order → Payment · 1:N

Для каждой связи показывать:

- Исходную сущность.
- Целевую сущность.
- Кардинальность.
- Подпись связи, если присутствует.

При выборе открывать редактор связи.

---

# 6. Контекстная панель свойств

В нижней части конструктора либо в отдельной изменяемой по размеру области отображать свойства выбранного объекта.

Панель должна быть динамической.

### Для участника Sequence

- Название.
- Алиас.
- Тип.
- Цвет.

### Для сообщения Sequence

- Отправитель.
- Получатель.
- Текст.
- Тип стрелки.

### Для управляющего блока

- Тип блока.
- Условие или подпись.
- Ветви.
- Допустимые операции.

### Для сущности ER

- Название.
- Алиас.
- Атрибуты.
- Поддерживаемые параметры оформления.

### Для связи ER

- Исходная сущность.
- Целевая сущность.
- Кардинальности.
- Подпись.
- Тип линии.

Использовать обычные поля ввода, выпадающие списки, переключатели и другие нативные компоненты.

**Не показывать исходный PlantUML-код вместо формы редактирования**, если соответствующий элемент поддерживается конструктором.

Если элемент не поддерживается, показывать объяснение ограничения и возможность перейти к его исходному коду.

# 7. Двусторонняя синхронизация

## 7.1. Конструктор → Код

При изменении элемента:

1. Определить связанный узел модели.
2. Проверить допустимость изменения.
3. Сформировать минимальное изменение исходного текста.
4. Применить изменение.
5. Обновить редактор.
6. Обновить диаграмму.
7. Сохранить выделение редактируемого элемента.

Не перезаписывать весь документ.

## 7.2. Код → Конструктор

При изменении исходного кода:

1. Повторно разобрать изменённый документ.
2. Обновить структурную модель.
3. Обновить соответствующие объекты дерева.
4. Сохранить состояние раскрытых групп, если их идентичность установлена.
5. Сохранить выделение, если выбранный объект продолжает существовать.

Не сбрасывать всю панель при каждом изменении текста.

## 7.3. Ошибки

Если код содержит синтаксическую ошибку:

- Не удалять элементы из исходного документа.
- Не выполнять небезопасные изменения.
- Показывать понятную диагностику.
- Сохранять последнее корректное состояние конструктора с отметкой о его неактуальности.
- Блокировать операции, которые невозможно безопасно применить.

# 8. Навигация между областями

Реализовать согласованную навигацию:

**Конструктор → Код**

Выбор объекта прокручивает редактор к соответствующей конструкции и подсвечивает её.

**Код → Конструктор**

При выборе поддерживаемой конструкции в редакторе соответствующий объект выделяется в дереве.

**Конструктор → Диаграмма**

При выборе объекта приложение пытается найти соответствующий визуальный элемент и выделить либо показать его.

**Диаграмма → Конструктор**

При выборе однозначно сопоставленного визуального элемента открывается соответствующий объект дерева и его свойства.

Если точное сопоставление SVG-элемента с исходной конструкцией невозможно, не выполнять приблизительное выделение.

Вместо этого предусмотреть безопасную навигацию через структурное дерево.

---

# 9. Управление элементами

Реализовать контекстные действия:

- Добавить.
- Редактировать.
- Дублировать, если операция поддерживается.
- Удалить.
- Переместить вверх.
- Переместить вниз.
- Перейти к коду.

Для вложенных элементов учитывать ограничения структуры.

Запретить перемещение, которое нарушает синтаксис или семантику диаграммы.

При удалении участника со связанными сообщениями не удалять эти сообщения молча. Предусмотреть подтверждение и безопасные варианты обработки зависимостей.

Все операции должны поддерживать Undo/Redo.

---

# 10. Настройки диаграммы

Технические конструкции не должны отображаться в общем дереве объектов сценария.

В частности:

- `skinparam`
- `autonumber`
- `title`
- Настройки шрифтов.
- Настройки цветов.
- Другие глобальные параметры.

Создать отдельный раздел **«Настройки диаграммы»**.

В нём показывать поддерживаемые глобальные параметры в виде обычных элементов управления.

Например:

- Автонумерация сообщений.
- Название диаграммы.
- Поддерживаемые параметры оформления.

Неподдерживаемые параметры сохранять в исходном коде без изменений.

Не пытаться автоматически интерпретировать произвольные `skinparam` как редактируемые свойства.

---

# 11. UX и визуальное оформление

Использовать существующую графитово-изумрудную дизайн-систему PlantUML Studio.

Требования:

- Компактное дерево объектов.
- Чёткая иерархия.
- Читаемые названия.
- Ненавязчивые иконки.
- Мягкая подсветка выбранных элементов.
- Поддержка Light / Dark / System.
- Контекстные действия без визуальной перегруженности.
- Сворачивание разделов.
- Сохранение состояния дерева при переключении вкладок.

Не отображать длинные PlantUML-строки как названия объектов.

Длинные подписи должны переноситься либо сокращаться с возможностью просмотра полного текста.

Правая панель должна иметь регулируемую ширину и возможность полного скрытия.

Область свойств также должна изменять размер либо сворачиваться.

---

# 12. Улучшение области диаграммы

Сейчас диаграмма занимает относительно небольшую часть центральной области.

Необходимо улучшить использование доступного пространства.

Реализовать:

- Регулируемую ширину панелей.
- Возможность скрыть конструктор.
- Fit to Window.
- Fit to Width.
- Масштабирование.
- Перемещение области просмотра.
- Сохранение масштаба при обновлении, если это возможно.

Не изменять алгоритм раскладки официального PlantUML.

# 13. Тестирование

Обязательно проверить:

1. Отображение участников по названиям.
2. Отображение сообщений по названиям.
3. Корректную вложенность `alt/else/opt/loop`.
4. Сворачивание и разворачивание блоков.
5. Отображение сущностей и атрибутов ER.
6. Отображение связей ER.
7. Редактирование свойств.
8. Добавление и удаление объектов.
9. Переименование участников и сущностей.
10. Синхронизацию конструктора и кода.
11. Сохранение комментариев и форматирования.
12. Обработку неподдерживаемых конструкций.
13. Работу Undo/Redo.
14. Сохранение выделения после обновления.
15. Работу на больших диаграммах.
16. Отсутствие регрессий существующего функционала.

Для проверки использовать сложные демонстрационные Sequence-диаграммы с вымышленными участниками и сценариями.

---

# 14. Критерии приёмки

Задача считается выполненной, если:

- Конструктор больше не представляет собой список исходных строк PlantUML.
- Участники отображаются как отдельные объекты с названиями и типами.
- Сообщения отображаются по смысловым названиям и направлениям.
- Управляющие блоки представлены иерархически.
- Сущности ER содержат вложенные атрибуты.
- Связи ER представлены отдельными объектами.
- Свойства редактируются через формы.
- Работает поиск по объектам.
- Работает добавление и удаление поддерживаемых элементов.
- Работает навигация между конструктором и кодом.
- Реализована безопасная синхронизация.
- Неподдерживаемые конструкции не повреждаются.
- Сохраняются комментарии и форматирование.
- Конструктор поддерживает обе темы приложения.
- Все основные операции покрыты тестами.

---

# 15. Порядок реализации

1. Проанализировать существующий конструктор и модель документа.
2. Определить доступные семантические объекты.
3. Спроектировать новое дерево Sequence и ER.
4. Реализовать структурную панель.
5. Реализовать контекстные редакторы свойств.
6. Подключить операции изменения исходного кода.
7. Реализовать навигацию и синхронизацию выделения.
8. Вынести глобальные настройки диаграммы в отдельный раздел.
9. Улучшить управление размерами панелей.
10. Провести тестирование и исправить регрессии.

Не переписывать приложение с нуля.

Не создавать альтернативную архитектуру редактора.

**Главный результат:** правая панель PlantUML Studio должна стать полноценным семантическим конструктором, в котором пользователь работает с участниками, сообщениями, условиями, сущностями и связями, а не с текстовыми строками PlantUML.
