# PlantUML Studio: ТЗ на v0.2 и v0.3

## Общие требования

Развивать существующее нативное macOS-приложение PlantUML Studio, не переписывая архитектуру и не создавая параллельные реализации уже существующих компонентов.

**Перед началом работы агент обязан:**

1. Изучить текущий репозиторий, README, архитектуру, тесты и документацию.
2. Определить фактическую готовность функциональности v0.1.
3. Изучить приложенный официальный гайд PlantUML.
4. Проверить существующие механизмы парсинга, рендеринга и двусторонней синхронизации.
5. Составить план реализации с указанием затрагиваемых модулей.
6. Не удалять и не изменять существующую функциональность без технической необходимости.

Вся новая функциональность должна соответствовать официальным возможностям PlantUML.

Не реализовывать собственные расширения синтаксиса `.puml`.

Сохранять исходный код, комментарии, форматирование и неподдерживаемые конструктором конструкции.

Все изменения должны сопровождаться тестами.

# Релиз v0.2: Productivity & UX

## 1. Цель

Превратить базовый редактор PlantUML в удобный инструмент для ежедневной работы с большими и сложными диаграммами.

Основной акцент:

- Быстрая навигация.
- Минимизация ручного редактирования кода.
- Горячие клавиши.
- Удобная работа со структурой.
- Повторное использование типовых конструкций.
- Стабильность и производительность.

## 2. Навигация по диаграмме

### 2.1. Структурная панель

Реализовать панель Outline, отображающую структуру текущего документа.

Для Sequence Diagram:

- Участники.
- Сообщения.
- Управляющие блоки.
- Вложенные условия.
- Заметки.
- Другие поддерживаемые структурные элементы.

Для ER Diagram:

- Сущности.
- Атрибуты.
- Связи.

Функциональность:

- Выбор элемента.
- Переход к соответствующему участку кода.
- Отображение свойств.
- Поиск элемента.
- Сворачивание и разворачивание групп.
- Контекстное меню действий.

### 2.2. Синхронизация выделения

Реализовать согласованное выделение элементов.

При выборе элемента в Outline:

- Подсвечивается соответствующий участок кода.
- Открываются свойства.
- Выполняется переход к элементу диаграммы, если его можно однозначно сопоставить.

При выборе поддерживаемого элемента диаграммы:

- Выделяется соответствующий элемент Outline.
- Выполняется переход к исходному коду.
- Открываются свойства.

При перемещении курсора в коде:

- Определяется текущий структурный элемент.
- Обновляется активный элемент Outline.

Если точное сопоставление невозможно, приложение не должно выбирать произвольный элемент.

### 2.3. Навигация по большим диаграммам

Добавить:

- Fit to Window.
- Fit to Width.
- Zoom In / Zoom Out.
- Reset Zoom.
- Перемещение области просмотра.
- Возврат к выбранному элементу.
- Сохранение масштаба и положения просмотра при обычном обновлении диаграммы, когда это возможно.

Масштабирование не должно менять исходный PlantUML-код.

## 3. Поиск

### 3.1. Поиск по коду

Поддержать:

- Поиск текста.
- Замену.
- Замену всех совпадений.
- Учет регистра.
- Поиск по регулярным выражениям.
- Переход между совпадениями.

### 3.2. Поиск по структуре

Реализовать отдельный поиск по элементам документа.

Sequence:

- Участники.
- Сообщения.
- Текст сообщений.
- Условия блоков.

ER:

- Сущности.
- Атрибуты.
- Подписи связей.

Результаты должны содержать тип элемента и его название либо краткое описание.

Выбор результата открывает соответствующий элемент.

## 4. Горячие клавиши

Реализовать стандартные macOS shortcuts и дополнительные команды.

Базовые:

| Комбинация | Действие |
|---|---|
| Cmd + N | Новый документ |
| Cmd + O | Открыть |
| Cmd + S | Сохранить |
| Cmd + Shift + S | Сохранить как |
| Cmd + F | Поиск |
| Cmd + Option + F | Поиск и замена |
| Cmd + Z | Отменить |
| Cmd + Shift + Z | Повторить |
| Cmd + Plus | Увеличить диаграмму |
| Cmd + Minus | Уменьшить диаграмму |
| Cmd + 0 | Вписать диаграмму |

Дополнительно реализовать настраиваемые команды для:

- Добавления участника.
- Добавления сообщения.
- Добавления блока.
- Добавления сущности.
- Добавления атрибута.
- Добавления связи.
- Переключения между кодом и диаграммой.
- Открытия панели свойств.

Все сочетания должны корректно работать с учётом фокуса и не конфликтовать со стандартными командами macOS.

---

## 5. Command Palette

Добавить единую палитру команд, открываемую через Cmd + Shift + P.

Функциональность:

- Поиск доступных действий.
- Выполнение команды с клавиатуры.
- Отображение горячих клавиш.
- Контекстная фильтрация команд.

Например, для Sequence должны предлагаться действия создания участников и сообщений, а для ER - сущностей и связей.

Недоступные команды должны быть скрыты либо явно обозначены как неактивные.

---

## 6. Быстрые действия конструктора

### 6.1. Sequence Diagram

Добавить удобные операции:

- Вставить сообщение до выбранного.
- Вставить сообщение после выбранного.
- Добавить ответное сообщение.
- Обернуть выбранные сообщения в `alt`, `opt` или `loop`.
- Дублировать сообщение.
- Дублировать управляющий блок.
- Переместить сообщение вверх или вниз.
- Переименовать участника во всём документе.

Все операции должны учитывать структурные ограничения.

Например, оборачивание сообщений в управляющий блок допускается только для непрерывного диапазона элементов с корректными границами вложенности.

### 6.2. ER Diagram

Добавить:

- Быстрое создание сущности.
- Добавление нескольких атрибутов.
- Дублирование сущности.
- Быстрое создание связи между выбранными сущностями.
- Изменение кардинальности через выпадающий список.
- Переименование сущности с обновлением связанных ссылок.

При дублировании автоматически обеспечивать уникальность алиаса.

---

## 7. Библиотека шаблонов

Реализовать локальную библиотеку PlantUML-шаблонов.

### 7.1. Встроенные шаблоны

Sequence:

- REST API Request / Response.
- Асинхронное взаимодействие.
- Обработка ошибки.
- Retry.
- Timeout.
- Альтернативные сценарии.
- Взаимодействие через очередь сообщений.

ER:

- Простая сущность.
- One-to-Many.
- Many-to-Many через промежуточную сущность.
- Набор связанных сущностей.

### 7.2. Пользовательские шаблоны

Пользователь должен иметь возможность:

- Сохранить фрагмент как шаблон.
- Назвать шаблон.
- Указать категорию.
- Изменить шаблон.
- Удалить шаблон.
- Вставить шаблон в документ.

Хранить шаблоны локально.

Перед вставкой проверять корректность контекста и конфликты идентификаторов.

Вставка не должна повреждать существующий документ.

Оптимизировать работу с большими документами.

Требования:

- Отмена устаревших задач рендеринга.
- Кэширование результатов.
- Инкрементальное обновление структурной модели там, где это технически оправдано.
- Отсутствие зависания интерфейса при ошибках рендеринга.

Провести тестирование на документах размером 100, 300, 500 и 1000 строк.

Зафиксировать время разбора, рендеринга и применения визуальных операций на тестовой машине.

Не вводить произвольные показатели производительности без измерений.

# Релиз v0.3: Architecture & Visual Diff

## 11. Цель

Расширить PlantUML Studio инструментами архитектурного проектирования и сравнения изменений.

Основные направления:

- Component Diagram.
- Структурное сравнение диаграмм.
- Удобная работа с версиями документов.
- Подготовка архитектурной документации.

---

## 12. Component Diagram

Добавить третий тип диаграмм.

Использовать официальный синтаксис PlantUML Component Diagram.

### 12.1. Элементы

Поддержать документированные конструкции, включая:

- component
- interface
- package
- node
- database
- cloud
- frame
- folder

Конкретный набор допустимых свойств определить по официальному гайду.

### 12.2. Операции конструктора

Реализовать:

- Создание элемента.
- Изменение названия.
- Изменение алиаса.
- Изменение поддерживаемого типа.
- Удаление.
- Создание связей.
- Изменение подписей связей.
- Изменение допустимых типов линий.
- Изменение вложенности элементов.
- Изменение поддерживаемых параметров оформления.

### 12.3. Контейнеры

Поддержать группировку элементов через официальные конструкции PlantUML.

Возможности:

- Создать контейнер.
- Добавить элемент в контейнер.
- Переместить элемент между контейнерами.
- Изменить название контейнера.
- Удалить контейнер с безопасной обработкой вложенных элементов.

Не допускать создания синтаксически некорректной вложенности.

### 12.4. Синхронизация

Component Diagram должна использовать общую инфраструктуру:

- Source Document.
- Parser.
- Document Model.
- Source Ranges.
- Text Edits.
- Renderer.
- Undo/Redo.

Не создавать отдельный независимый механизм синхронизации.

Все визуальные изменения должны преобразовываться в допустимые конструкции PlantUML.

### 12.5. Ограничения

Не реализовывать:

- Свободное позиционирование элементов.
- Собственный движок раскладки.
- Произвольное рисование соединений.
- Нестандартные расширения PlantUML.

---

## 13. Visual Diff

Реализовать инструмент сравнения двух версий PlantUML-документа.

### 13.1. Источники сравнения

Поддержать:

- Два локальных `.puml` файла.
- Текущий документ и сохранённую версию.
- Два открытых документа.

### 13.2. Текстовый Diff

Реализовать сравнение исходного кода.

Отображать:

- Добавленные строки.
- Удалённые строки.
- Изменённые строки.

Поддержать синхронную прокрутку и переход между изменениями.

### 13.3. Структурный Diff

Реализовать сравнение элементов поддерживаемых диаграмм.

Sequence:

- Добавленные и удалённые участники.
- Изменённые участники.
- Добавленные и удалённые сообщения.
- Изменённые сообщения.
- Изменения управляющих блоков.
- Изменение порядка элементов.

ER:

- Добавленные и удалённые сущности.
- Изменённые атрибуты.
- Изменённые связи.
- Изменения кардинальностей.

Component:

- Добавленные и удалённые компоненты.
- Изменённые связи.
- Изменения контейнеров.
- Изменения вложенности.

Для сопоставления элементов использовать структурные признаки и контекст.

Не считать совпадение имён достаточным доказательством идентичности элементов.

При неоднозначности показывать изменение как неопределённое либо использовать текстовый Diff.

### 13.4. Визуальное представление

Реализовать режим сравнения с двумя диаграммами рядом.

Функциональность:

- Side-by-side Preview.
- Синхронное масштабирование по выбору пользователя.
- Переход между изменениями.
- Панель списка различий.
- Выделение структурных изменений, для которых установлено достоверное соответствие исходным элементам.

Если невозможно точно сопоставить изменение с графическим объектом, отображать его в структурном списке и коде.

Не использовать приблизительное выделение, которое может вводить пользователя в заблуждение.

# 19. Общие требования к реализации

Для обоих релизов:

1. Работать с существующим репозиторием.
2. Не переписывать готовые компоненты без обоснования.
3. Соблюдать принятые соглашения по коду.
4. Не добавлять неиспользуемые зависимости.
5. Не создавать демонстрационные заглушки вместо функциональности.
6. Не допускать потери пользовательских данных.
7. Обеспечивать локальную работу без обязательного интернета.
8. Поддерживать светлую и тёмную темы macOS.
9. Сохранять совместимость с обычными `.puml` файлами.
10. Обновлять README и архитектурную документацию.

Каждый релиз реализовывать отдельно.

Сначала завершить и протестировать v0.2, затем переходить к v0.3.

Перед началом каждого релиза создать отдельную Git-ветку от актуальной рабочей ветки проекта.

Не выполнять автоматическое слияние с основной веткой без подтверждения пользователя.

По завершении предоставить:

- Список реализованных функций.
- Список изменённых модулей.
- Результаты тестирования.
- Известные ограничения.
- Инструкцию по проверке.
- Предложение на слияние ветки.

**Главный приоритет: корректность PlantUML и сохранность исходного документа важнее количества реализованных функций.**
